# ctaudit — 研究アイディアのまとめ

## 0. 一行サマリ

**LLMエージェントを実行せずに、「攻撃者が影響しうる入力 → LLMの判断 → 危険なツール」という制御依存フロー(CWE-1426)を静的解析で検出するシステム。** 核心の新規性は、通常のテイント解析が途切れる「LLMによる動的なツール選択(=壁)」を、健全に具体的なツールへ解決すること。


## 1. 問題設定

### 1.1 何が危険か
LLMエージェントは、攻撃者が影響しうる入力(プロンプト、ユーザ入力、外部データ/RAG、**ツールが取得した内容**など)をLLMに読ませ、その出力で次に呼ぶツールを決める。攻撃者がデータの中身でLLMを誘導し、コマンド実行・ファイル書き込み等の危険なツールを呼ばせる——これが **CWE-1426(モデル出力を十分に検証せず信頼する問題)**。

### 1.2 なぜ既存手法で捉えにくいか(差別化の起点)
- **暗黙的フロー(implicit / control-dependency flow)**である。攻撃者データの「値」が危険操作に渡るのではなく、データが「**どのツールを呼ぶかの判断**」に影響する。値の伝播だけを追う通常のテイント解析では捉えにくい。
- テイント解析は**動的なツール選択の箇所で途切れる**。呼び出し先が実行時まで決まらないため、その先へ汚れを運べない。先行研究(TaintP2X, ICSE'26)も、reflection・動的import・runtime code generation で静的解析が "struggle する" ことを自らの限界として明記している——ここが本研究のニッチ。


## 2. 中核アイデア

> LLMを経由する箇所でテイント解析が途切れるので、**LLMが呼びうるツールをすべてその箇所に当てはめて**テイント解析を続ける。全部当てはめるのは非効率なので、**ありえない組み合わせは除外**する。

核はシンプル。研究としての価値は「**除外をいい加減にやらない規律**」にある:

- **候補を全部当てはめる**(壁が呼びうるツールを列挙し、各々にフローを続ける)= 過大近似、**見落とさない(recall優先)**。
- **確実な根拠があるときだけ絞る**(固定の表・許可リストに基づく)。根拠がなければ残す。これにより「効率化」ではなく**精度(無駄な誤検出の削減)**を、見落としを増やさずに実現する。


## 3. 設計の規律(一貫した4方針)

1. **意味論はLLM、健全性・再現性は決定的解析。** ツールの意味理解などに補助的にLLMを使うが、フロー判定・絞り込みは**決定的**に行う。ここで重要な区別として、解析には**2つのLLM**が登場する:①解析対象エージェントが内部で使うLLM(構造の一部)、②ctaudit がツール把握を補助するために使う補助LLM(解析の道具)。**フロー判定は②に依存しない。**
2. **recall最優先。** 見落とさないことを最優先。絞り込みは確証があるときだけ。
3. **健全性を軽々しく主張しない。** 「健全(sound)」と言うには証明が要る。実際の挙動(根拠があれば絞る、なければ残す)を正確に述べる。
4. **対象外の明示。** LLMフリーの動的ディスパッチ(CWE-470)、LLMがコード自体を生成する型(registry-narrowing の前提が崩れる)は対象外。


## 4. システム構成(2段階)

**段階1:ツール把握(分類)** — 各ツールが source か sink かを判定。本体に危険な呼び出し(`subprocess`/`exec`/`eval` 等)があるか、どの引数が危険箇所に届くかを見る。

**段階2:壁の解決(resolve_dispatch)** — 壁(動的ディスパッチ)が呼びうる候補ツールを列挙し、確実な根拠で絞る。各検出は経路の来歴(どの source・どのLLMノード・どの壁・どの sink)を保持し、フローを完全に再構成できる。

**provenance(来歴)**:各検出は `source_marks`(どの source / file:line)、`exit_sites`(通過したLLMノード)、`via_dispatch`(どの壁の式)、`sink_site`、`framework_candidates`(登録ツール集合)を保持。`kind="implicit"` ⟺ source が存在し制御経由で繋がっている。


## 5. 本研究で実装した拡張

採用したのは**項目1のみ**(他の改訂案は却下)。フレームワーク対応を宣言的な支持部品として追加し、さらにrecall方向(方向B)・precision方向(方向C)に展開した。

### 5.1 項目1 — フレームワーク・ディスパッチ仕様(DispatchSpec)
元のシステムは、壁を**ユーザコードに見える構文** `TOOL_MAP[name](...)` としてしか検出できなかった(手動ループ型)。しかし**実エージェントの多くはフレームワーク管理型**——`create_react_agent(llm, tools=[...])` + `.invoke()` のように、ディスパッチが LangGraph の ToolNode 等フレームワーク内部に隠れる。これを構文スキャンは取りこぼす。

- **`DispatchSpec`(宣言的仕様)**:各フレームワークの「登録API(どの引数がツール集合を定義するか)」と「起動API(どれがディスパッチ壁か)」を宣言。LangChain/LangGraph の `create_react_agent`/`create_agent`/`AgentExecutor` × `.invoke`/`.stream`/`.ainvoke` を仕様化。**フレームワーク本体には貫通せず、既知の意味論を宣言的に吸収するだけ。**
- **設定可能な絞り込み**:登録ツール集合を「候補列挙のみ(デフォルト・保守的)」か「信頼して絞り込む」かを選べる。
- **副次的改善**:変数束縛のツールリスト解決(`tools = [...]; create_react_agent(llm, tools)`)、`Tool(func=...)` ラッパー展開、フレームワーク登録された未デコレート関数のツール認識(登録自体をツール性のシグナルとする)。

### 5.2 方向B — 既知の危険ライブラリツールの認識(recall向上)
実エージェントは危険操作が**ライブラリ内部**にある組み込みツール(`PythonAstREPLTool`, `ShellTool`, `PythonREPL` 等)を多用する。本体スキャンでは接地できない。

- **宣言的レジストリ**(クラス名→sinkカテゴリの表)で既知ツールの sink 意味を供給。`DispatchSpec` と同じ「宣言的知識」の思想。
- 構築連鎖を解決:`x = PythonAstREPLTool()` / `Tool(func=python_repl.run)` → `python_repl = PythonAstREPLTool()` / `Tool(func=ShellTool().run)`。
- **エージェントに実際に登録された**変数のみ sink 化(構築だけして未登録は flag しない)。

### 5.3 方向C — ツール内部の引数到達性解析(precision向上)
本体に危険呼び出しがあるだけで sink 判定していたため、引数を無害化するツールも誤検出していた。関数内テイント解析で「引数が実際に危険箇所に届くか」を判定:

- **`reaches`**:パラメータが危険箇所に到達(直接/代入/f-string/連結/コンテナ)→ high維持
- **`not`**:どのパラメータも到達せず引数が定数・非パラメータ由来(例:パラメータを辞書キーにしか使わない)→ **lowに降格**
- **`unknown`**:判断不能(呼び出し経由・属性・未解決)→ 維持

**核心の制約 — sink は決して削除しない。** `not` でも**降格のみ**。判断できないものは `unknown` で維持。だから不完全なフロー解析でも最悪「真の検出が high のまま残る」だけで、**見落とし(FN)は絶対に作らない**。recall最優先と一貫。


## 6. 評価:何が測れて何が測れないか(重要な認識)

### 測れること
- **precision**:検出された各件を「source→LLM→危険ツールにコード上で到達するか」で TP/FP 判定(分母=検出件数)。
- **構成的GT(自作fixture)での recall**:正解が既知なので FN が分かる。

### 測れないこと
- **実レポジトリでの全体 recall**:システム内の危険フロー全体を網羅把握できない(FN の分母が定まらない)。だから実レポでは「全体 recall は測らない」と明記。

### 三層評価
1. **構成的fixture**(recall=precision=guard=1.000、ただし「自作ゆえ当然」と正直に明記)。
2. **実レポジトリ**(全体recallは測らず、検出の正しさを目視 TP/FP。判定基準=フロー到達、悪用可能性は範囲外)。
3. **既知CVE**(調査の結果、**動的ディスパッチを含むCVEはほぼ存在しない**と判明。これ自体が「この経路が未分析」という動機を補強。CVE検証は主軸にしない)。

CVE調査の詳細:AutoGPT CVE-2024-1881/6091 はディスパッチされたツールの**引数**処理であってディスパッチ自体ではない。Vanna CVE-2024-5565・LlamaIndex CVE-2024-3098 は単一ホップの eval でディスパッチではない。Cursor CVE-2025-54135/54136 は config/MCP。**厳密な動的ディスパッチCVEの希少性そのものが本研究の動機を支える。**


## 7. 実証結果

### 7.1 システム現状
**152テスト全pass。flow_bench recall=1.000 precision=1.000(TP=10 FP=0 FN=0)。framework_dispatch_bench 5/5。tool-model benchmark precision=100% recall=46.2%。**

### 7.2 構成的ベンチ(framework_dispatch_bench)
フレームワーク3形態(`create_react_agent`/`AgentExecutor`/`create_agent`+stream)で壁を検出・解決(3/3)。安全版は誤検出なし(1/1)。手動ループ版も従来どおり検出(1/1)。**「同じ脅威を手動版とフレームワーク版で用意し、両方検出できる」=構文スキャンが取りこぼすフレームワーク版を項目1が回収する**という差別化を直接実証。

### 7.3 実リポ検証(公開5件、静的解析のみ、判定=フロー到達)

| 対象(出典) | 書き方 | sinkの場所 | 結果 |
|---|---|---|---|
| dylancastillo | `@tool` + `exec` | ユーザコード | ✓ `run_python_code` |
| langgraph_supervisor | 未デコレート関数 + `os.popen` | ユーザコード | ✓ `run_command` |
| botextract | `Tool()`ラッパー + `PythonAstREPLTool` | **ライブラリ内部** | ✓ `python_repl_tool`(方向B) |
| a2a_calculator | **クラス BaseTool** + `eval` | ユーザコード | ✓ `calculator` |
| maxscheijen | **dict-registry + 生OpenAI SDK** | ユーザコード | **✗ 既知の限界** |

**フレームワーク系の4つの書き方(関数デコレータ/素の関数/ラッパー/クラス)はすべて壁を検出し具体sinkまで解決。** ライブラリ内部sinkも方向Bで解決。実コードを試したことで「未解決」に複数の原因(ツール認識ゲートの取りこぼし=修正済み / ライブラリ内部sink=方向Bで解決 / 手書きdict-registry=限界)を切り分けられた——これは fixture だけでは見つからなかった発見。


## 8. 既知の限界(正直に明記)

1. **宣言的知識は人手・バージョン依存。** フレームワーク仕様・既知ツール表は対象バージョンを固定。表にないものは拾えない。
2. **grounding のボトルネックは残る。** 段階1は「本体に危険呼び出しがあるか」「引数が届くか」を見るが、関数内解析にとどまる。方向Cで「壁の解決」と「個々ツールの sink 判定」は**分離**され、残る難しさは後者に局所化された。
3. **手書きdict-registry のツール認識は未対応(5件目)。** メソッド分割(壁とLLM呼び出しが別メソッド)については、**recall安全な1ホップの手続き間制御伝播**を追加し、壁を検出できるようにした(`self.agent.invoke` のインスタンス属性束縛、およびLLM由来引数をヘルパーに渡す手動ディスパッチ)。**フル手続き間解析は健全性・recall方針と衝突するため意図的に避け、1ホップに限定**。残るのは、手書き dataclass 経由の素の関数のツール認識(デコレータ/BaseTool/フレームワーク登録のいずれにも当てはまらない)と、生SDKの source/exit の細部。5件目はこれにより「壁が見えない」→「壁検出・未解決」へ前進。
4. **動的コード生成型エージェント**(LLMがツールを選ぶのでなくコード自体を生成)は registry-narrowing の前提が崩れ対象外。


## 9. 今後の方向

- **手書きdict-registry / 手続き間フロー**(5件目の限界):手書きレジストリのモデル化、または関数をまたいだ制御領域の伝播。これまでより大きめの変更。
- **方向Cの深化**:関数内解析を超えた、より精密な引数到達解析(ただし健全性を主張しない/recallを犠牲にしない設計を維持)。
- **フレームワーク仕様の拡張**:MCP / OpenAI Agents の `DispatchSpec`(同じ枠組み。OpenAI Agents は既に Runner を ExitSpec で扱うため二重計上に注意)。
- **既知ツール表の拡充**、**実リポをさらに増やす**(別パターンでの検出傾向)。


## 10. まとめの一言

**シンプルな核(壁で全ツールを当てはめ、確実な根拠でだけ絞る)を、「見落とさない規律」と「壁の宣言的解決」で厳密な静的監査に仕上げた研究。** 本セッションで射程を**実エージェントの大多数を占めるフレームワーク利用型**まで広げ(項目1)、**ライブラリ内部sink**も解決可能にし(方向B)、**precision**を recall を犠牲にせず改善し(方向C)、公開実リポ5件で「多様な書き方で壁を検出し具体sinkまで解決できる」ことと、「手書きdict-registry型はまだ解けない」という境界の両方を実証した。
