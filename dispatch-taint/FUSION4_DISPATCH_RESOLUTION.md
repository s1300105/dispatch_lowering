# Fusion #4 — resolving the dispatch wall with the shared tool model

## The problem (the "dispatch wall")

The **dataflow leg** (`ctaudit/analysis/taint_engine.py`) follows taint along concrete
code paths, modelling the LLM call as a taint join (`join@LLM`) so control-dependency
flows (CWE-1426) become representable. But a **dynamic-dispatch** site has a callee
chosen at runtime:

```python
TOOL_MAP[call["name"]](**call["args"])      # subscript callee
get_function(call["name"])(**call["args"])  # higher-order callee
getattr(tools, name)(**args)                # getattr callee
```

A static name-matcher cannot say *which* concrete tool — hence which sink — the
(attacker-influenceable, control-tainted) arguments reach. The engine handles this
precisely: `_is_dynamic_callee` recognises the three shapes and, **only when control
taint actually reaches the site**, records a `kind="dispatch"` finding — the wall. That
finding already carries the path context the enumeration leg lacks:

* the **source marks** on the tainted path (which tool outputs),
* the **LLM nodes** (`exit_sites`) the control taint passed through,
* CFG **reachability**, and any **guard** observed at the dispatch site.

What it *cannot* give on its own is the concrete sink.

## The fix (fusion #4)

`ctaudit/analysis/dispatch_resolution.py : resolve_dispatch(findings, model)` takes the
localised-but-unresolved dispatch findings together with the shared
`RepoToolModel` (auto-generated by the #5 classifier) and resolves the concrete target
set: the dispatcher can route to any registered tool, so **each registered sink tool
becomes a concrete resolved flow**, inheriting the dispatch finding's path context and
gaining the sink's name / category / severity / guard. Each resolved finding is tagged
`via_dispatch=<dispatch expr>` for provenance.

This is strictly more informative than either leg alone:

* **vs the enumeration leg** (SOURCES × SINKS cross-product): only the sinks reachable
  *through a real control-tainted dispatch path* are emitted, and the path's source
  marks / LLM nodes are preserved — not a blind product over every source × every sink.
* **vs the dataflow leg alone**: the wall is defeated — concrete, named, guarded sinks
  instead of an opaque `dispatch?` node.

### Recall-first / safety

* If the model has **no** sink tools (nothing to resolve to), the original dispatch
  finding is **kept** (`keep_unresolved=True`) — the wall is still reported.
* Guards on resolved findings come from the **deterministic tool model** (the tool's own
  / cross-layer guard from #5), falling back to a guard observed at the dispatch site —
  **never invented here**, and conservative (`None` ⇒ unguarded / high priority).

## Worked example (`fixtures/dynamic_dispatch_agent.py`)

A LangGraph-style loop: untrusted tool output → `ToolMessage` → `add_messages` reducer →
`llm.invoke(...)` (exit) → model-chosen `{name, args}` → `TOOL_MAP[name](**args)`.

```
leg-a (dataflow):
  1 finding — DISPATCH WALL
  source[<tool-output>@…:62]  ==(history)==>  llm[…:54]  ==(tool_calls)==>  TOOL_MAP[call["name"]]@…:59

fusion #4 (resolve against the tool model {run_cmd: code_execution, fetch_url: network, echo: benign}):
  [RESOLVED] run_cmd    code_execution  high    [resolved from dispatch TOOL_MAP[call["name"]]]
  [RESOLVED] fetch_url  network         medium  [resolved from dispatch TOOL_MAP[call["name"]]]
  (echo has no sink role -> not emitted)
```

Both resolved findings preserve the path's source marks, the LLM node, and reachability.

## Usage

```python
from ctaudit import analyze_path
from ctaudit.analysis import resolve_dispatch
from ctaudit.toolmodel import get_classifier

findings = analyze_path("path/to/app.py").findings          # dataflow leg (may contain dispatch walls)
model    = get_classifier("deepseek").classify("path/to/repo")  # shared tool model (#5)
resolved = resolve_dispatch(findings, model, repo="path/to/repo")  # fusion #4 + registry narrowing
```

Passing `repo=` enables **target narrowing** (below); omitting it resolves to the
repo-global sink set (conservative, recall-first).

## Target narrowing (precision, recall-first)

A dispatch reads a specific registry, e.g. `TOOL_MAP[name](**args)`. When `repo` is
given and that registry is a **single static dict literal that is never mutated**, its
membership is *complete*, so the dispatch can only reach the tools registered in it.
`resolve_dispatch` then narrows the target set to `sinks ∩ registry-members`, dropping
sinks that live in a *different* registry. Worked example on
`fixtures/dynamic_dispatch_agent.py` (`TOOL_MAP = {fetch_url, run_cmd, echo}`), with a
model that also contains a `db_query` (SQL) sink registered elsewhere:

```
repo-global (repo=None)     : db_query, fetch_url, run_cmd     # over-enumerates db_query
narrowed   (repo=fixtures)  : fetch_url, run_cmd               # db_query dropped (not in TOOL_MAP)
```

Recall-first fallbacks — the resolver stays repo-global (never silently drops a sink it
isn't sure about) when the registry can't be confidently mapped:
* a **mutated / dynamically-built** registry (`REGISTRY[k] = …`, `.update(…)`, a
  comprehension, or non-literal members) is *untrusted*;
* a **higher-order** callee (`get_function(name)(…)`, `getattr(…)(…)`) has no statically
  named registry;
* a registry redefined more than once.

When membership *is* trusted and no sink is a member, the dispatch provably reaches no
sink and nothing false is emitted.

## Phase / tool-name whitelist gate narrowing

On top of registry narrowing, the resolver applies a second, sound narrowing when the
dispatch's **key variable** is gated by a dominating membership check against a trusted
tool-name whitelist — the codecli `PHASE_TOOLS` shape:

```python
allowed = PHASE_TOOLS.get(phase, [])      # PHASE_TOOLS: dict[Phase, list[str]]
if name not in allowed:                    # gate on the dispatch key `name`
    continue                               # (early exit)
TOOL_MAP[name](**args)                      # dispatch
```

A tool whose name is in no whitelist value is provably rejected by the gate, so the
resolver intersects the targets with the **union of the whitelist's members**. Worked
example on `fixtures/phase_gated_agent.py` (`run_cmd` is in `TOOL_MAP` but in no phase):

```
repo-global                 : run_cmd, write_file
registry + phase gate (repo): write_file              # run_cmd dropped (never phase-allowed)
```

Sound + recall-first: the whitelist must be an unmutated dict-of-string-lists (or flat
string set), the guard must check the *same* variable the dispatch indexes with, and it
must dominate the dispatch (an early-exit `if key not in WL: …` before it, or the dispatch
nested under `if key in WL:`). A mutated whitelist is untrusted (its static union may
under-count) → no phase narrowing. We narrow to the **union** of all phases; per-phase
narrowing would need phase-state tracking.

Tests: `tests/test_dispatch_resolution.py` — wall localisation; concrete resolution with
path-context + guard preservation / non-invention; recall-first when the model has no
sinks; non-dispatch passthrough; **narrowing to the dispatch's registry**, the
**repo-global fallbacks**, and the **phase/whitelist gate** (drop a never-whitelisted sink;
recall-safe when the whitelist is mutated).

## Scope / limits

* Phase narrowing is **intra-procedural**: the gate must dominate the dispatch in the same
  function. codecli's real split — the gate in `execute_tool_call` protecting a `run_tool`
  call that dispatches one frame deeper — is interprocedural and not yet linked, so on
  codecli itself the resolver narrows by registry only (conservative). Modelling that link
  is future work.
* The dataflow leg records a dispatch only under **control** taint (the attacker-
  influences-the-LLM's-choice case). A purely-data dispatch is out of scope by design.

## Wired into the hybrid driver

`hybrid.py` runs fusion #4 end-to-end: after the enumeration leg it builds the shared #5
model from the target and resolves every dispatch wall (narrowed) before merging with the
Pysa leg.

```bash
# offline (heuristic model): an idiom the heuristic can't classify leaves the wall (recall-safe)
python hybrid.py pysa/projects/hybrid_demo/src --pysa-results pysa/projects/hybrid_demo/res

# DeepSeek model: discovers the @classmethod tool behind REGISTRY, so the wall resolves
python hybrid.py pysa/projects/hybrid_demo/src --pysa-results pysa/projects/hybrid_demo/res \
       --classifier deepseek
#   [..] LLM dispatch -> resolved sink (CWE-1426)  [ctaudit-enumerate, fusion#4-resolved]
#        sink : execute_shell_command (code_execution) ... [resolved from dispatch REGISTRY[call.function.name]]

python hybrid.py <target> --no-resolve        # leave walls unresolved (before/after)
```

Resolved findings are tagged `fusion#4-resolved`, keep the path's source/LLM-node trace
(`[resolved from dispatch …]`), and are triaged like any other finding. Tests:
`tests/test_hybrid.py` (resolution + provenance/trace/triage, `--no-resolve` keeps the
wall, recall-safe when the model has no sink, narrowing to registry members).
